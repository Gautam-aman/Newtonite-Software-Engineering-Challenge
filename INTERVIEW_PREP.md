# Interview preparation

Use the code and tests as your source of truth. Read `ItemService`, `ItemRepository`, `TeamAccess`, the Flyway migration and the integration tests before presenting.

**Architecture in 60 seconds.** A React/TypeScript browser uses TanStack Query to call a same-origin Spring Boot API. Spring Security authenticates an opaque bearer session. Controllers validate DTOs; the service checks team permissions and business rules; Spring JDBC talks to PostgreSQL. Flyway owns schema evolution. One database transaction contains a work-item mutation and its history. Nginx serves the built frontend and proxies API calls in Compose. There is no worker in this version.

**Why Java/Spring?** Java 21 and Spring Boot provide explicit DTOs, validation, security filters, managed transactions, connection pooling and mature PostgreSQL tests. The trade-off is a larger framework/runtime than a small scripting service. JDBC was selected over JPA because SQL concurrency predicates and cursor queries are central to this assessment and are easier to review directly.

**Two simultaneous claims.** Both requests authenticate and check team membership. Each attempts one UPDATE whose predicates require the same version, OPEN and no assignee. PostgreSQL locks the row and rechecks the predicate after the competing transaction. One updates; the other affects zero rows and returns 409. The winner increments version and inserts CLAIMED before commit. Rollback frees the row without a false success event.

**Stale writes.** The UI sends its observed version. The service locks the row for edits/transitions/comments, checks the current owner and role, then compares versions. UPDATE also contains a version predicate. Mismatch produces 409; no item or history change commits. Explicit refresh lets the user review current state. We do not silently merge conflicting descriptions.

**Idempotency.** A retry uses the same principal, create operation and key. PostgreSQL advisory transaction locking serializes matching requests across JVMs; a uniqueness constraint defines the exact key scope. Typed request JSON is SHA-256 hashed. The item, CREATED event and original response are committed together. Identical retries return the original snapshot; changed payloads get 409. No TTL/cleanup is implemented, so storage grows until an explicit retention design is added.

**Authorization.** A membership is `(user, team, role)`. Every resource read/write checks the item's team in `TeamAccess`; lists use a membership predicate in SQL. Viewer reads. Member creates/claims/comments and edits or advances assigned work. Lead/Admin additionally reassign, reprioritize, approve and reject. A Lead may approve their own work; two-person review is not a requirement we invented. The UI controls are usability aids; direct API calls still face checks.

**Transactional history.** Spring's public service methods are `@Transactional`; all JDBC operations share the same managed connection. If an audit insert fails, the whole transaction rolls back. The test injects an audit trigger failure and confirms no item or idempotency record persists. A database trigger also rejects audit UPDATE/DELETE. An administrator with schema-owner privileges could disable this; we do not claim tamper-proof compliance storage.

**Indexes and pagination.** Team/creation ordering and ID tie-breaker support the primary list; status and priority variants support queues; assignee/creation supports personal work; the partial due-date index supports overdue items. Trigram GIN accelerates selective substring search. Explain that combinations may need a sort or bitmap plan, and common one-character searches may scan. Keyset pagination avoids OFFSET growth but does not offer random page numbers or a consistent snapshot across requests.

**Database unavailable.** Connection acquisition is bounded. New reads and writes fail with a consistent 503; tokens also cannot be authenticated while PostgreSQL is unavailable. Failed transactions roll back. The browser shows an error and supports retry, with a 15-second request timeout. After uncertain create responses, reuse the same key to recover the result. No automatic failover or availability guarantee is claimed.

**Worker crash.** There is no asynchronous worker in this implementation. Nothing is silently queued or dropped. If notifications were added, persist an outbox row alongside assignment, use a leased SKIP LOCKED claim, retries/backoff with a terminal failed state, and a unique consumer key. A crash after sending but before acknowledging means delivery is at least once; the consumer must deduplicate. Never claim exactly-once external delivery.

**At 10× scale.** Measure query plans, latency and connection use first. Add indexes supported by actual selective query patterns; keep pagination bounded. Stateless API replicas can share PostgreSQL's concurrency rules, but pool sizes must fit its connection budget. Consider separate credentials, expiry cleanup, per-principal rate limits, audit partitioning, and read replicas for tolerant dashboards. Introduce a queue/search engine only when measured requirements justify the extra consistency and operations burden.

**Add a workflow state live.** Add the enum to `Contracts.Status`, a new Flyway migration to change the check constraint (never edit an applied migration), update `ItemService.transition`, frontend status lists/transition controls/style and documentation. Add allowed/forbidden transition tests and rerun PostgreSQL/UI checks. Consider how existing rows should reach the state.

**Change Lead permissions live.** Start with the documented matrix. Change the centralized role check and affected service rules, then frontend controls. Add direct API tests for allowed and forbidden users, including a Lead who is only Member in a second team. Do not rely on hiding the button.

**Compromises.** No outbox, attachments, SSO, signup/provisioning, team administration, delete/reopen, realtime subscriptions, user notifications, password recovery, rate limiting, deployment or demo video. Admin equals Lead within its team. Token reload requires login. Full list totals are omitted to avoid a count query per page; dashboard counts are separate aggregate queries. There is no full accessibility certification or load/availability benchmark. The initial Java migration uses PostgreSQL-specific functions by design.

## A 100-word submission decision

I made PostgreSQL the authority for concurrency and accountability rather than relying on browser state or JVM locks. Claims use a conditional update requiring an unassigned item and the expected version, so simultaneous requests produce one winner. Edits and workflow transitions reject stale versions. Each successful mutation and its audit event share one transaction. Creation retries use durable, principal-scoped idempotency records and transaction-scoped advisory locks. These choices keep behavior consistent across application instances while remaining easy to inspect and explain. The trade-off is PostgreSQL-specific SQL and additional integration tests, which I preferred over silent overwrites or distributed infrastructure without need.
